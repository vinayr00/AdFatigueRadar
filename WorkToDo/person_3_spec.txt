8. P0 Replay Architecture
The replay has two layers:
Scenario generator — creates potential-world curves and comment streams.
Runtime simulator — applies current campaign state/actions to the potential world and emits observed telemetry.
Person 3 owns layer 1.
Person 2 owns the shared runtime ActionSimulation behavior in layer 2.
Do not duplicate layer 2 inside replay/scenarios/.
9. Required Three-Day Replay
Duration: 72 simulated hours.
Compute step: 5 minutes.
Guard window: 60 minutes.
Starting comment rate: approximately 2/minute.
Healthy/lull comment rate: approximately 0.4/minute.
Stress comment rate: approximately 8/minute.
Healthy phase: hours 0–18.
Early fatigue: hours 18–36.
Acceleration: hours 36–52.
Economic degradation: hours 52–72.
Potential-world telemetry must continue to exist independently of action state.
Telemetry must be plausible and internally consistent, but these values are demo parameters—not real-world claims.
10. Potential-World Curves
Generate deterministic curves for:
potential impressions / volume
potential CPM
potential CTR
potential conversion rate
potential comment intensity
potential comment category mix
optional reach
optional frequency
Every scenario must have an explicit seed.
The same seed must produce the same potential-world curves.
Protected and no-action runs must start from identical potential-world curves.
Action state changes observed volume, spend, and conversions; it must not rewrite the underlying potential world.
11. Action-Responsive Replay
ACTIVE:  observed_volume = potential_volumeSOFT_REDUCED:  observed_volume = potential_volume × 0.80PAUSED:  observed_new_volume = 0  observed_new_spend = 0  emit zero-volume heartbeat telemetry every 5 minutes
Person 3 does not implement a competing action multiplier.
Person 2's ActionSimulation is the authority for runtime action application.
12. CPA / Conversion Handling
Compute rolling-hour ratios from sums.
CPA = spend / conversions when conversions > 0.
CPA = null when conversions = 0.
Never emit infinity for CPA.
Economic risk is N/A below 20 conversions in the rolling hour.
Do not manufacture conversions simply to make Path A pause.
13. Scenario Design Requirements
13.1 Healthy
Stable sentiment/category mix.
Healthy CTR/frequency.
Stable economic metrics.
No action should occur.
13.2 Early Fatigue
Increase fatigue/mild mockery categories gradually.
Sentiment decay should begin before economic degradation.
Audience risk may reach WARNING before economic confirmation.
13.3 Acceleration
Increase comment acceleration and harmful weighted share.
Increase frequency and/or CTR decay.
The scenario must allow SOFT_REDUCED to occur naturally from the risk engine.
13.4 Economic Degradation
Degrade CPA/CPM/ROAS/conversion-rate potential curves.
The scenario should permit Path A pause after the configured evidence/persistence gates.
Do not hard-code a pause event.
14. Lead-Time Requirement
The project target is detection of negative sentiment acceleration before significant CPA degradation. The demo scenario is designed so economic degradation begins at hour 52. Tuning must verify whether WARNING occurs before hour 28. Do not claim a 24-hour lead until held-out reporting seeds demonstrate it.
Person 3 owns scenario generation/tuning mechanics.
Person 2 owns the measured lead-time analysis and final risk-gate interpretation.
Do not tune reporting seeds to guarantee the target.
15. Negative-Control Scenarios
15.1 CPM-Only Negative Control
Increase CPM materially while keeping audience-risk evidence below pause conditions.
Expected behavior: no combined pause.
Use this to show that CPM alone is not sufficient.
15.2 Banter Storm
Generate high-volume banter/meme comments.
Keep economics stable.
Category should remain banter_meme where appropriate.
Expected behavior: combined guard must not pause.
Sentiment-only baseline may false-positive; this is intentional for the baseline comparison.

19. Frontend State Rules
Display backend state as the source of truth.
Do not infer PAUSED from a frontend timer or local state.
Display economic risk as N/A when backend reports insufficient conversions.
Display CPA as — or equivalent null representation when no conversions exist.
Do not render raw HTML from comments.
Escape comment text using the framework's normal safe rendering.
Do not expose API keys, provider secrets, HMAC secrets, or server environment values.
If the backend reports stale data, display it clearly rather than silently treating it as fresh.
